## Project overview

This repository contains the team project for the course **Advanced Analytics and Applications (Summer Semester 2026)**. The project studies how a German automotive company could plan and operate a fully electric ride-hailing fleet. Chicago taxi trips serve as a case study for urban ride-hailing demand.

The analysis covers four main steps:

1. cleaning, validating, enriching, and aggregating trip-level data;
2. analysing temporal demand, spatial hotspots, origin-destination flows, weather effects, and resolution choices;
3. predicting demand with support vector machines and neural networks; and
4. optimising a simplified private-charging problem with dynamic programming and reinforcement learning.

The written report translates these results into strategic, tactical, and operational implications for a potential fleet operator.

## Data

The supporting input files are provided in `data/`. Only the Chicago taxi-trip CSV is excluded from Git because it is approximately 6.9 GB and must be downloaded separately. The `processed/` folder is generated by Task 1 and is also not part of the repository.

The expected contents are:

```text
data/
|-- Taxi_Trips_(2024-)_20260502.csv   Download separately (not tracked)
|-- chicago_weather_hourly.csv        Included
|-- chicago_weather_daily.csv         Included
|-- chicago_community_areas.geojson   Included
|-- comed_prices_raw.csv              Included
`-- comed_alpha_profile.csv           Included
```

### Chicago taxi trips

The taxi-trip CSV is the only input file that is not included in the repository. Download the official [Taxi Trips (2024-)](https://data.cityofchicago.org/Transportation/Taxi-Trips-2024-/ajtu-isnz) dataset from the City of Chicago Data Portal. The analysis uses the period from 1 January 2024 through 31 March 2026. Apply this date range before exporting the CSV and save it as:

```text
data/Taxi_Trips_(2024-)_20260502.csv
```

Task 1 reads the complete 6.9-GB file and therefore requires sufficient disk space and memory.

### Weather data

The included hourly and daily weather files come from the [Open-Meteo Historical Weather API](https://open-meteo.com/en/docs/historical-weather-api). They were downloaded using the Chicago-centroid coordinates and settings stored in the Task 1 notebook:

- coordinates: latitude `41.85`, longitude `-87.65`;
- period: `2024-01-01` to `2026-04-01`;
- timezone: `America/Chicago`;
- units: Fahrenheit, inches, and mph;
- hourly variables: temperature, precipitation, rain, snowfall, weather code, and wind speed;
- daily variables: weather code, mean temperature, sunshine duration, precipitation, rain, snowfall, precipitation hours, and maximum wind speed.

They are provided under the filenames expected by Task 1:

```text
data/chicago_weather_hourly.csv
data/chicago_weather_daily.csv
```

The files retain the three Open-Meteo metadata rows because Task 1 skips these rows when loading them. The exact preconfigured download links are documented in Section 1.5 of `task1/Task1_optimized.ipynb`.

### Community Area boundaries

The included GeoJSON contains the official [Chicago Community Area boundaries](https://data.cityofchicago.org/Facilities-Geographic-Boundaries/Boundaries-Community-Areas/igwz-8jzy) used by Task 2:

```text
data/chicago_community_areas.geojson
```

If the file is missing, Task 2 downloads it automatically from the [City of Chicago GeoJSON endpoint](https://data.cityofchicago.org/api/geospatial/igwz-8jzy?method=export&format=GeoJSON).

### Electricity-price data for smart charging

The project does **not** use a dataset of real charging sessions. Charging demand is derived from the taxi data and modelled synthetically. The price-profile rationale is based on ComEd's official [5-minute electricity-price API](https://hourlypricing.comed.com/hp-api/).

The included files were created by the download cell in `task4/task4.ipynb`, which requests ComEd prices for 1 January 2024 through 30 April 2026:

```text
data/comed_prices_raw.csv
data/comed_alpha_profile.csv
```

The final smart-charging model does not read these files directly. It uses a manually stylised price profile in the code whose temporal shape is based on the downloaded ComEd prices. The files document the empirical source and the intermediate average profile.

## Environment setup

The project uses Python 3.12 and [uv](https://docs.astral.sh/uv/) for dependency management.

### Prerequisites

- Python 3.12
- uv
- [Quarto](https://quarto.org/docs/get-started/)
- a LaTeX distribution for PDF output

From the repository root, create the environment and install the locked dependencies:

```bash
uv sync
```

For PDF rendering, TinyTeX can be installed through the Quarto CLI:

```bash
quarto install tinytex
quarto check
```

Run this command directly with Quarto, not through `uv`. An existing TeX Live or MiKTeX installation can be used instead.

## Running the analysis

Run the notebooks in the following order:

1. `task1/Task1_optimized.ipynb`
2. `task2/Task2_optimized.ipynb`
3. `task3/Task3_optimized.ipynb`
4. `task4/xyz.ipynb`

Task 1 creates the files in `processed/` used by all later tasks. Task 2 reads those aggregates. Task 3 additionally writes trained models and comparison results to `models/`. The current Task 4 notebook requires `processed/df_trips_full.parquet`, but is otherwise independent of Tasks 2 and 3.

The notebooks use paths relative to their own folders, such as `../data` and `../processed`. When running them interactively, open the repository as the workspace and execute each notebook from its existing folder.


Task 1 processes a multi-gigabyte CSV, while the model searches in Task 3 can take substantial time. Running a notebook in place also replaces its saved outputs and may overwrite files in `processed/` or `models/`.

## Building the report

The report is assembled from `report.qmd` and the chapter files in `sections/`. From the repository root, render the PDF with:

```bash
quarto render report.qmd --to pdf
```

The generated report is available at [docs/report.pdf](docs/report.pdf).

The Quarto report uses the saved text, tables, and figures in the repository; rendering the report does not rerun the analysis notebooks. Rerun the relevant notebooks first only when their results need to be updated, then ensure that the corresponding report text and figures are updated as well.
